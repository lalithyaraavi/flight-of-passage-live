I once waited three hours for Flight of Passage.

So I mapped the wait times and cut my next wait in half. This is that project rebuilt as a real pipeline. Every 10 minutes it reads the posted wait for every ride in Disney's Animal Kingdom, cleans it, checks itself, and publishes the tables this page reads.

Station 4 · quality checks

The pipeline keeps an eye on itself

Live feeds are messy. The feed sometimes stops refreshing, GitHub starts scheduled runs late, fetches fail, and now and then a wait jumps in a way no real line does. Every run checks for each of these, keeps the raw snapshot regardless, and holds bad readings out of the tables above.

pipeline/sql/*.sql

The "best hour to ride" is one window query. For every reading, average the next 60 minutes of readings, then keep the window with the lowest average.

WITH windows AS (
  SELECT park_date, local_time,
         avg(wait_min)   OVER w AS win_avg,
         count(wait_min) OVER w AS win_n
  FROM fop
  WINDOW w AS (PARTITION BY park_date ORDER BY m
               RANGE BETWEEN CURRENT ROW AND 60 FOLLOWING)
)
SELECT park_date,
       arg_min(local_time, (win_avg, m)) AS best_start,  -- earliest of any ties
       round(min(win_avg), 1)            AS best_avg
FROM windows
WHERE win_n >= 3                     -- one lucky reading isn't an hour
GROUP BY park_date;

Station 7 · at Disney scale

What I'd change for hundreds of millions of plays

Spark and Delta instead of Python and CSV. The PySpark silver job is already in the repo. At scale its output becomes a Delta MERGE on the event key, so reruns never double-count, partitioned by date.

Airflow instead of cron. The DAG is in the repo too. On a real cluster, sensors would wait for late data instead of guessing, and the gate would hold a bad hour back from the dashboards.

The checks as a shared library. Freshness, duplicates, schema drift and impossible jumps written once, so every pipeline in the Data organization checks itself the same way.
